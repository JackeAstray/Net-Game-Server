# Game 项目详细架构与技术文档

## 一、 项目定位
`Game` 项目（`NetGameServer.csproj`）即游戏引擎后端的“主脑节点”。承担整个网游/服务架构里面所有的计算最重、玩家互动最频繁的虚拟游戏世界（Scene/Room）管理功能，是整体性能监控与内存管理的重灾区。作为一个 `<OutputType>Exe</OutputType>`，该服属于整个生态最内层的一端，通过外部 `Gateway` 引入流量与指令，对外交互绝不裸奔。

## 二、 核心技术栈与依赖
本身是核心的游戏纯业务集成体，除了目标定在 `net10.0` 外，它严格只做业务依赖，因此强捆绑了：
- **`Network` 项目**: 提供服务器与终端长链接的支持引擎能力。
- **`Shared` 项目**: 解析所有消息，使用全局定义好的配置/通信类进行内部传递调度与读取通用配表设置。
*(不包含其他的复杂三方 Nuget，保持了代码最纯净的调度态)*

## 三、 详细模块拆解 (基于常规核心架构推断)

### 1. 服务端入口 (`Program.cs`)
- 此文件是整个虚拟世界的创建执行者。
- **启动与监听配置**: 调起内部的 `NetworkManager` 对内网提供 Tcp/Kcp/Websocket 监听。
- **服务注册**: 把针对 “进入游戏”、“移动”、“释放技能”、“购买物品”的不同请求（对应着各个数据网络通讯 `Handler`）全量注入注册到路由中心 `MessageRouter`，准备开始收发处理。

### 2. 世界主循环/物理同步(主程核心逻辑/未列明但必然存在的设计)
因为是即时联机 Server，不可避存在下列框架模型：
- **World Management**: 存放全局所有的 `Room`、`Scene`、或者全区全服的世界级管理器（处理地图范围划分/多端玩家广播）。
- **Tick / Update Loop**: 高精度服务器计时器模块。一般为维持在一秒 10-60 次频率循环的独立后台线程调度游戏事件的推演。(如怪物AI寻路推进一次、玩家的 buff 计时一跳等)。

### 3. 数据层联动通信
- **Redis / DB 分发层**: 通过 MQ 桥接机制或后台挂起的方式下潜到数据库更新该区服玩家最新的游玩进程以及活动结算。

## 四、 开发规范
1. **防止多线程破坏**: `Game` 开发时必须时刻注意数据抢占；由于多用户高频访问各自状态以及互动交互产生竞态条件，通常主张把一个房间或者一个角色的数据变化限制投递在唯一的主控 `ID` 下归属的串行队列当中，或者采用全服 `Tick单线程处理状态模型` 去做数据流传更新，严禁随随便便在不同 IO 并发回调里面加锁修改全局/玩家数值。
