# Login 项目详细架构与技术文档

## 一、 项目定位
`Login`（账户登陆服务器节点）是一个极度隔离并且高度状态无涉的关键辅助核心服务。现代网游的业务要求在进行大量的非游戏动作通讯（例如密码校验、异地防封禁锁、手机实名制绑定以及大热天的游戏开服瞬间大量玩家登录进队队列调度）等高 I/O、高网络交互但低实时物理帧同步逻辑的情况时，分离出来专门接受这一系列动作的微服务。这保证了哪怕这瞬间服务器爆满排队崩溃了，里面在刷本吃鸡玩游戏的人依旧不受卡顿波动影响。

## 二、 核心技术栈与依赖（推断自架构和职责定位）
在现有的项目体系下，它通常承接基于 `Network` 内封好的对端接收实现，可能用到：
- **GRPC / HTTP REST**: 基于配置接受并响应高频但不保持状态的 JSON Token 申请（由于包含 `Controllers` 等文件命名可能深度融合了 `ASP.NET Core WebAPI` 管线特性）。
- **缓存与数据库通信**: 登录服务器要向 `DB` 系统或是集中化的 Redis 高频验证并调出身份信息文件，因此可能作为微服务参与 `DB`（直接操作或者通过 RPC 接口代理请求）。

## 三、 详细模块拆解

### 1. 业务逻辑控制/入口调度层
- **`Controllers/AccountController.cs`**:
  常用于做网页版入口/客户端版本检测等简单强求。提供 HTTP 式的接口：接受设备/用户提交的一套包括哈希散列处理后密码与账号名匹配请求，返回状态 JSON 或者一个合法的 Token。
- **`Handlers/LoginHandler.cs`**: 
  用于响应 TCP/其它强长联机底层管道打进来的登录指令包，处理 `LoginMessages` 定义的数据验证和转发下发的包。

### 2. 用户态保持和登陆临时态 (`Managers/SessionManager.cs`)
- 玩家还没进入 `Game` 之前的驻客站。
- 该类会为初步校验成功的玩家建立预定状态签发 Token（例如通过 JWT 颁发令牌，存到 Redis 里缓存生命周期20秒），向目标用户返回他接下来要去哪个内网 `Gateway/Game区服` 的终点站连接信息以及一次性通关暗号。
- 同一账号互踢安全控制（顶号登录处理流程）也会被优先截停或集中拦截在这发生。

### 3. 应用入口与服务监听注册 (`Program.cs`)
- 初始化 ASP.NET Core 的依赖容器。
- 设定验证规则及绑定给登录专用的外部独立监听端口/路由前缀设置。

## 四、 开发规范
1. **强安全检查和日志记录**: 该层是抗外界注入暴力破解的第一块阵地，所以所有进入的登录请求必须受到速率限制和极高频率的异常记录抓取（Serilog/Log 输出预警）。
2. **轻量与隔离化**: 和 `Gateway` 类似，一旦分配好身份发放行证交给客户端走人，那么登录服立刻就不再持有和关注这位玩家了，严禁让登录服一直维系跟内网玩家长时间交互的长生命周期 Socket 不放手。
